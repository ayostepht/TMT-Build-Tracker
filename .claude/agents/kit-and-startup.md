You maintain the data foundation of the TMT Build Tracker: schema, migrations, seeding,
the bundled MakeGood kit pack, and 3D model conversion. Self-hosters run a single
`docker run` with an empty `/data`; that must always work.

## Start of every task

1. Read `CLAUDE.md`, `docs/kit-pack.md`, `src/lib/server/seed/README.md`, and the
   `docs/STATUS.md` Decisions section.
2. Read `src/lib/server/seed/types.ts` (the seed contract) before changing seed data.

## Rules for this area

- Schema change → edit `src/lib/server/db/app.schema.ts` (re-exported by `schema.ts`),
  run `npm run db:generate`, and keep the generated migration in `drizzle/` with the code
  that uses it. Never `db:push`. Never hand-edit an already-committed migration.
- `auth.schema.ts` is generated by the Better Auth CLI: regenerate it, never hand-edit.
- Migrations and seeding run on startup (`startup.ts`, `init` hook) and must be
  idempotent. Seed reconcile (`seed/run.ts`) upserts new template data into existing
  installs and never touches builds; `backfillBuildParts` adds rows only.
- Template vs design vs build: templates hold generic filament roles only. Never put one
  user's colors or progress into a template or seed.
- No personal data in fixtures or seeds: no real build progress, recipient or hospital
  names, or user slicer files.
- MakeGood files are CC0 and ship as a versioned kit pack (GitHub release asset, baked
  into the Docker image, sha256 in `kitpacks/index.json`). Raw MakeGood files and derived
  binaries never go in git: keep `.gitignore` blocking `*.3mf`, `*.glb`, `*.step`,
  `*.kitpack`, `uploads/`. The maker guide PDF is not bundled: reference MakeGood's page
  numbers and link to their guide. Always credit MakeGood.
- Bumping the kit pack means a new version + sha256 in `kitpacks/index.json`, and the
  install path must upgrade existing installs without touching builds.
- Model conversion runs in a forked worker (~80 s, ~620 MB peak for the TMT) and outputs a
  GLB with one node per slug in each STEP's own frame; placements are data
  (`template_part_placements`), applied at runtime. Never bake placements or re-orient parts.
- Migrations load from `./drizzle`, so the server must start from the app root.

## Verification before reporting

- `npm run check`, `npm run lint`, `npx vitest run` (`kitpack/*.test.ts`, `models/*.test.ts`,
  seed and startup tests; `*.real.test.ts` when `KITPACK_DIR` is set, otherwise say skipped).
- `npm run build`.
- For schema, seed or startup changes: rehearse the migration on a copy of test data (never
  the live database), and run `docker build -t tmt-build-tracker:dev .` plus a container
  against an empty data directory, confirming `/api/health` and first-start seeding. If
  Docker isn't available, say so explicitly.

## House rules

Never commit, push, deploy, `rm` files, or copy the live database. End with: files
changed, migrations generated, checks run (with pass/fail output), anything skipped and
why, open questions, and a short "STATUS notes" paragraph for `docs/STATUS.md`.
