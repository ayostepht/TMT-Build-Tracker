# Part 1: Audit

## 1. Security

### Critical

**C1. Any signed-up user can make the server connect to any host and port.** [checked]
Every account owns a personal workspace, so every "editor" endpoint is open to anyone who
registers. `parseHost` (`src/lib/server/printers/store.ts:74-80`) checks characters only;
ports 1-65535 are accepted. `POST /api/printers/camera-test`
(`src/routes/api/printers/camera-test/+server.ts`) needs no saved printer and returns the
fetched frame as a data URL. The "same host" camera guard compares against a host the caller
chose. Also reachable [sweep]: `POST /api/printers/test`, `POST /api/printers/discover` (UDP
broadcast on the server's LAN), the Spoolman URL (`src/lib/server/spoolman/client.ts`), and
adapter fetches that follow redirects (OctoPrint, Moonraker token, Spoolman). Effect on a
public host: port scanning and reading of the host's internal network, and visibility of the
maintainer's own printers and cameras. `TMT_PRINTERS=off` stops only the background
supervisor, not these endpoints.

### High

- **H1. Pending invitations can be claimed by registering the invitee's email.** [sweep]
  Email is never verified (`src/lib/server/auth.ts:41` [checked]); the onboarding page lists
  invitations matching the signed-in email. Exposes recipient, hospital and handoff data.
- **H2. Site admin can be claimed.** [checked] `isSiteAdmin`
  (`src/lib/server/access.ts:81-91`) grants admin to the earliest-created user or to any
  unverified email listed in `ADMIN_EMAILS`. Admins replace the kit model every user loads.
- **H3. Sign-up is open with no switch.** [checked] No invite-only mode, approval, CAPTCHA
  or limit on chapters. (Known: STATUS Security.)
- **H4. Request bodies up to 1.1 GB can be buffered in memory.** `BODY_SIZE_LIMIT=1100M` is
  global (`Dockerfile:32` [checked]); JSON routes, photo form data, design snapshots and the
  prototype import read the whole body before checking size [sweep].
- **H5. No quotas.** [sweep] Unlimited builds, photos, printers (each a standing outbound
  connection), kit copies, 200 MB STEP uploads through one install-wide conversion queue
  with a 20-minute timeout, and 3MFs up to 1 GB.
- **H6. Sign-in rate limiting can be sidestepped; the app's own API has none.**
  `withClientIp` (`src/hooks.server.ts:18-27` [checked]) passes a client-sent
  `X-Forwarded-For` through untouched. Better Auth limits are library defaults: in-memory,
  `/api/auth/*` only [sweep]. Behaviour depends on whether the proxy overwrites or appends
  the header. (Known: STATUS Security.)

### Medium

- **M1. Weak secrets accepted.** [checked] `docker-compose.example.yml:19` ships
  `BETTER_AUTH_SECRET: change-me` and `authSecret()` (`src/lib/server/config.ts`) accepts
  any non-empty value. Printer credentials are encrypted with a key derived from it [sweep].
- **M2. Cookies are `Secure` only when `PUBLIC_URL` is https** (`auth.ts:38` [checked]).
  Correct for LAN use; a public install that forgets `PUBLIC_URL` gets non-Secure cookies.
- **M3. No security headers.** [sweep] No CSP, HSTS, frame protection, Referrer-Policy;
  `nosniff` on two routes only.
- **M4. No password reset, account deletion or data export; no privacy or terms page.**
  [sweep] A forgotten password needs a database edit. The app stores recipient names,
  hospitals, contact notes and photos that may show children.
- **M5. Deleting a chapter leaves its files on disk.** [sweep]

### Low [sweep]

Templates readable by id across workspaces (ids are random); live-update streams outlive
membership removal; internal error text returned from two upload routes; printer name logged
unsanitised; sign-up reveals whether an email exists; no `npm audit`, Dependabot or image
scan in CI.

### Already done well

Access helpers used on every build, printer, photo, upload and design route with 404 for
non-members; no IDOR found among API routes; CSRF origin check on; no `{@html}`, no raw SQL
building, no `exec`; uploads stream to disk with byte caps, magic-byte checks and random
names; photos are type-sniffed and metadata-stripped; invitations are owner-only, random,
48 h, single-use; container runs as `node` with a healthcheck; no seeded accounts.

### Not determined

Whether OIDC login auto-links to an unverified password account with the same email;
whether the STEP worker's memory cap limits WASM; which `X-Forwarded-For` behaviour the
production proxy will have.

## 2. UX

### The daily loop (highest priority)

- **Starting a plate is 3 taps, 2 page loads and a scroll** from landing; the landing page
  is a build list with nothing about what is printing, and Overview has no start button or
  "next up". [sweep; landing and Overview confirmed live]
- **"Finish & log print…" opens with no result chosen**; the other two log buttons
  preselect Success (`NowCard.svelte` has no `quick`, `LogPlateButton.svelte:48` does).
  [checked]
- **Statuses go stale after the phone sleeps.** The build layout reconnects its live feed
  but only updates the status dot; it does not re-fetch
  (`src/routes/(app)/builds/[id]/+layout.svelte:31-37` [checked]). Risk: double logging.
- **Every tap waits for two round trips**; only Design colours update optimistically.
  [sweep]
- **Start/log lives in three places** (Print, Files, Overview) with four labels; deleting a
  log confirms in one place and not in another. [sweep]
- **Undo lasts 8 s**, then fixing a log is about 6 taps; the per-part status control and
  "Take off printer" have no undo. [sweep]

### Phone shell [checked, measured at 390 × 844 on the live copy]

- **Print tab: 346 px (41%) of the screen is pinned** by the sticky tab bar (47 px) plus
  the sticky filter toolbar (299 px), and they cover plate headings while scrolling.
- **About 440 px of header** sits above the first content; the first plate on Print starts
  near 800 px.
- **The tab bar clips "Settings"**; it is reachable only by sideways scroll.
- No bottom navigation; the top bar wraps to 2-3 rows.

### Navigation and wording

- **One concept, four names**: chapter, workspace, team, "My builds" (URL `/teams/`).
- "Builds ▾" is never highlighted inside a build; "All builds" shows one workspace only;
  `/designs` has no nav entry; `/onboarding` is not onboarding. [sweep]
- **"Pause" on a printer card pauses monitoring, not the print** [checked live and in
  `PrinterForm.svelte:298`]. In a read-only app this wording invites a wrong guess.
- Colour editing exists twice (Design tab, Settings → Filament). [checked live]
- **Changing a colour mid-build shows no "plates and export are out of date" notice in
  Design**; it appears only in Files. [sweep]

### Page length [checked live, 1440 px]

Files is about 10,800 px tall and Finish about 11,100 px; Print is about 9,000 px on phone.
Finished plates and completed steps are not collapsed.

### First run and smaller flows [sweep]

- Empty state for a new user is "No builds yet." with no explanation of the app.
- Wizard "Continue" is never blocked; Export can be reached with no printer. Builds started

- Invite: role defaults to viewer, no Copy button, member removal has no confirmation.
- Exporting one plate is about 6 taps; the slicer choice resets to Orca each time.

- **Settings: "Spools (kg)" inputs overflow the card** at 1440 px. [checked live]

The Now card (live progress, camera, pace-adjusted finish time); the Design tab on both

# Part 2: Proposal

## Decisions (maintainer, 2026-11-10)

1. **The public instance is SSO-only, with Google and GitHub.** No passwords there.
   **Self-hosted** offers SSO (OIDC) or email/password, plus a
   `SIGNUP=open|invite|closed` switch. No email verification and no SMTP anywhere. On
   self-hosted installs H1 and H2 are therefore mitigated by the sign-up switch, not closed:
   an owner who leaves sign-up open accepts that anyone who can reach the server can
   register an invited or admin address. Password reset stays an admin task there.
2. **Printers on the public instance: off now, bridge later.** Server-side printer
   connections are refused in `public` mode; the bridge (Stage 6) follows launch.
   Self-hosted installs keep today's behaviour, limited to private address ranges.
3. **README becomes Docker-first** with Unraid, reverse proxies, SSO, backups and printers
   as separate guides. This revises the earlier STATUS decision (Unraid + NPM + Authentik).
4. **Remove both** the prototype import and the 3D re-orientation code.

Still open, asked at the stage that needs them:

- **One name for the team concept** (Stage 2). Recommend "chapter" for shared spaces and
  "My builds" for the personal one; retire "workspace" and "team" from the UI.
- **Squash migrations before 1.0** (Stage 4). Recommend yes; needs a journal reset on the
  test copy.
- **Password reset on self-hosted installs** (Stage 1): with no email, a forgotten password
  needs an admin. Recommend a site-admin "set a temporary password" action or a documented
  CLI command.

### Stage 6: Printer breadth

1. **Harden what exists**: `https`/`wss` and path prefixes for Moonraker and OctoPrint;
   hardware checks of Moonraker, OctoPrint and Bambu by volunteer makers; the pending
   supervisor test through a full print.
2. **Auto-link reliably**: put plate numbers in exported plate/file names so jobs match
   without typing.
3. **Bridge for the public instance**: per-printer API token and an inbound status endpoint,
   plus a small companion container makers run at home that reads their printer with the
   existing adapters and pushes status out. Outbound-only from the home network; keeps the
   read-only rule. This is what makes automation work on the hosted version.
4. **Generic inbound sources** on the same endpoint: OctoPrint/Moonraker webhook recipes,
   Home Assistant automation, OctoEverywhere notifications (already on the STATUS list).
5. **New adapters**, in order of maker demand: Prusa Link, Duet/RepRapFirmware, Bambu
   camera. Document Creality K1/K2 as Moonraker.

All of Stage 6 gets `security-reviewer`. [printers]

### Stage 7: Public launch

Host with https `PUBLIC_URL`, `TMT_MODE=public`, SSO providers and trusted-proxy settings; nightly
backup of the database **and** `uploads/` with a tested restore; uptime check on
`/api/health`; a soft launch with one or two chapters before announcing.

## Suggested order

0 → 1 and 2 in parallel → 3 → 4 → 5 → 7, with Stage 6 items 1-2 alongside Stage 4 and item
3 (the bridge) after launch.
